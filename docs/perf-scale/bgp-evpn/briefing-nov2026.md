## Executive Summary

The scale ladder ran three times, growing from four lanes to five. Each run fixed what the
previous one exposed, so the measurements are now clean enough to act on.

**Queue wait is proportional to the generated object count, and the fit is tight.** Across the
four single-worker lanes of run 3, `wait p99 = 0.1335 to 0.1352 s x (nodes x RAs)`, a 1.3%
spread, while work duration is `0.1698 s x nodes` identical to four decimals in all four.
Doubling nodes doubles both; doubling RouteAdvertisements doubles the wait and leaves the work
untouched. That is what one apiserver write per node, queueing behind a single worker,
predicts.

**Hypothesis 1 is confirmed and reproduced three times.** 78 to 80% of RouteAdvertisements
reconciles during churn write nothing, and every wasted reconcile writes exactly one object
per node.

**Raising threadiness helps by half as much as a local run suggested.** Four workers cut the
queue wait 2.06x at twelve nodes, not the 4.01x measured on a four-node laptop cluster,
because work duration doubled at the same time. The contention that local run could not
explain scales with the worker count.

**Both instrument defects the earlier runs exposed are fixed and verified.** Nothing is
saturated and every snapshot converged, so this is the first run where no figure carries an
asterisk.

## Result 1: widening the buckets, and why the result is trustworthy

`ExponentialBuckets(.001, 2, 16)` reaches 32.768 s. Run 42220334668 pinned both 40-RA lanes
there. Run 42229126637 used 20 buckets, reaching 524.288 s.

| Lane | Run 1, 16 buckets | Run 2, 20 buckets | Run 3 | |
|---|---|---|---|---|
| density | 16.302 s | **16.269 s** | 16.056 s | unchanged — control |
| density-wide | 32.178 s | **32.440 s** | 32.342 s | unchanged — control |
| density-deep | 32.768 s *(pinned)* | **65.208 s** | 64.881 s | was hiding a factor of 2 |
| churn | 32.768 s *(pinned)* | **61.669 s** | 64.061 s | was hiding a factor of 1.9 |

The two lanes that were never saturated did not move. That is what makes the other two
believable: the rebucketing moved the ceiling, not the measurement. **Resolved**: nothing has
sat on a boundary since, and run 3 reproduces run 2 within 1.5% on every lane.

Only this family needed it. `route_advertisements_reconcile_duration_seconds` uses a `.005`
base and reaches 40.96 s; its highest reading is 2.163 s. Queue wait is the term that outgrows
the rest because it accumulates over the whole queue while work duration stays per item.

## Result 2: both axes collapse into one equation

Run 3, the four single-worker lanes:

| Lane | Nodes | RAs | Objects | Wait p99 | **Wait / object** | Work p99 | **Work / node** |
|---|---|---|---|---|---|---|---|
| density | 6 | 20 | 120 | 16.056 s | 0.1338 | 1.019 s | 0.1698 |
| density-wide | 12 | 20 | 240 | 32.342 s | 0.1348 | 2.038 s | 0.1698 |
| density-deep | 12 | 40 | 480 | 64.881 s | 0.1352 | 2.038 s | 0.1698 |
| churn | 12 | 40 | 480 | 64.061 s | 0.1335 | 2.038 s | 0.1698 |

```
queue wait p99 = 0.1335 to 0.1352 s x (nodes x RAs)   four points, 1.3% spread
work duration  = 0.1698 s x nodes                     identical to four decimals
```

The churn lane fits the same line despite doing 4.5x the reconciles, which is worth noting:
the extra work it generates queues on the same terms as the rest.

Work depends only on node count, because a reconcile is one apiserver write per node. Wait
depends on the **product**, because every generated object queues behind every other through a
single worker. The wait-to-work ratio is therefore just the RA count: 16.0x at 20 RAs, 32.0x
at 40.

This supersedes the October model, which had only the node axis. The RA axis was unmeasurable
until the buckets were widened.

**Extrapolation**, at 0.1355 s per object with `Threadiness: 1`:

| Shape | Objects | Predicted queue wait |
|---|---|---|
| 24 nodes x 40 RAs | 960 | 2.2 min |
| 120 nodes x 50 RAs | 6,000 | 13.6 min |
| 500 nodes x 50 RAs | 25,000 | 56.5 min |
| 500 nodes x 1000 RAs | 500,000 | **18.8 h** |

## Result 3: hypothesis 1 confirmed, and reproduced

The churn lane holds 40 RouteAdvertisements steady and deletes and recreates 4 of them, five
times. Run 2:

| | At creation complete | At run end | Churn-attributable |
|---|---|---|---|
| Reconciles | 107 | 196 | **+89** |
| `unchanged` writes | 804 | 1,872 | **+1,068** |
| `create` writes | 480 | 480 | **0** |

**Every churn reconcile was pure waste.** 1,068 / 89 = **12.0 writes per reconcile**, exactly
the node count, and not one of them a create. Each regenerated the full configuration for its
RouteAdvertisements, compared it, found it identical, and wrote nothing.

Across the whole run, **156 of 196 reconciles (80%) produced no configuration change**.

### What reproduces and what does not

| Quantity | Run 1 | Run 2 | Run 3 | |
|---|---|---|---|---|
| Writes per wasted reconcile | 12.0 | 12.0 | 12.0 | exact |
| Share of reconciles writing nothing | 80% | 80% | 78% | stable |
| `unchanged` writes | 1,956 | 1,872 | 1,680 | within 15% |
| Churn-attributable reconciles | +127 | +89 | +140 | **varies** |
| Amplification per RA changed | 6.35x | 4.45x | 7.00x | **varies** |

The invariants are stable; the amplification factor is not. That is an artifact of the
analysis rather than the system: splitting creation from churn depends on which 30 s sample
first shows `create` reaching 480, and the three runs crossed that threshold at different
points. Read the amplification as **4.5x to 7x** and the waste share, 78 to 80%, as the solid
figure.

Run 3 also recorded 4 `delete` operations where the earlier runs recorded none. The slower
settle gave the controller time to observe a deletion before the recreate, rather than
coalescing the pair — which is the behaviour the caveat below predicts and mild evidence that
the amplification is understated.

!!! note "Why the density lanes cannot show this"

    They create each RouteAdvertisements once and nothing else changes, so there is no
    amplification to observe: all three report exactly one reconcile per RA and zero
    `unchanged` writes. The October briefing marked hypothesis 1 confirmed on indirect
    evidence and then [withdrew it](08-first-ci-results.md#corrections). The churn lane was
    built to settle it, and has now done so twice.

**This likely understates the problem.** kube-burner recreates a deleted object about a second
after deleting it, and `create` never increased during churn, so the controller never observed
the gap and coalesced each pair into one event. Real churn, seconds or minutes apart, would
produce two fan-out events rather than one.

## Result 4: the settle heuristic fails intermittently, and spread proves it

`wait_for_settle()` in the hook polls every 5 s and declares convergence when the generated
count and total `runningConfig` bytes match the previous poll. frr-k8s reloads nodes in waves
and the total plateaus between them, so two matching polls do not mean converged.

Adding per-node spread to the comparison makes it unambiguous:

| Lane | Run 1 spread | Run 2 spread | Run 3 spread | Run 3 waited |
|---|---|---|---|---|
| density | 6 B (0.1%) | 9 B (0.1%) | 0.0% | 35 s |
| density-wide | 8 B (0.1%) | **3,385 B (31.1%)** | 0.0% | 40 s |
| density-deep | **3,928 B (23.2%)** | **2,616 B (13.8%)** | 0.0% | 40 s |
| churn | 103 B (0.5%) | 99 B (0.5%) | 0.5% | 10 s |
| density-threads | — | — | 1.8% | 15 s |

The distribution was bimodal — 0.1 to 0.5% against 14 to 31%, nothing between — and **wide
flipped between runs on an identical shape**, so it was a race rather than a property of the
larger lanes. Every node carries all 40 networks, so at convergence they must agree; a spread
of a quarter of the value is reload waves in flight.

!!! success "Fixed and verified in run 3"

    The hook now settles on **node agreement** rather than on the total holding still: it
    waits until `max - min` across nodes falls under 2% of the mean, keeping the stability
    check as a second condition. The threshold was chosen from the gap in the measured
    distribution, and replaying the byte counts from all eight earlier lane-runs through it
    accepts every converged snapshot and rejects every unconverged one.

    Run 3 is the result. Every lane converged, and the two that previously snapshotted early
    now wait 40 s where they used to stop at 10 to 25 s. Their config sizes rose
    correspondingly: deep reads 20,458 B per node against the 16,948 B it reported while
    mid-reload, a fifth higher. The hook records `converged`, `waitedSeconds` and
    `nodeSpreadPermille` in every snapshot, so no future reader has to derive this by hand.

Every snapshot is now trustworthy, so all three shapes have converged readings:

| Shape | Config per node | Across runs |
|---|---|---|
| 6 nodes, 20 RAs | 11,512 B | 11,609 / 11,512 / 11,512 — 0.8% |
| 12 nodes, 20 RAs | 11,454 B | 11,454 twice, identical |
| 12 nodes, 40 RAs | 20,458 to 20,652 B | three lanes in run 3 within 1% |

**Config size is independent of node count** — 6 and 12 nodes both give ~11.5 kB at 20 RAs —
and grows with network count at roughly **454 B per RA**. Linear extrapolation puts the 1.5 MB
etcd object limit near **3,300 networks**.

## Result 5: threadiness helps, by half what a laptop suggested

`bgp-ra-density-threads` is `bgp-ra-density-deep` with four reconcile workers instead of one.
Identical nodes, RouteAdvertisements, objects and waits, so the difference is the worker count
and nothing else.

| | deep, 1 worker | threads, 4 workers | |
|---|---|---|---|
| Queue wait p99 | 64.881 s | **31.457 s** | 2.06x better |
| Work duration p99 | 2.038 s | **4.076 s** | 2.00x worse |
| Reconcile p99 | 1.274 s | 5.047 s | 3.96x worse |
| Wait / work ratio | 31.8x | 7.7x | |
| Cluster manager CPU, max | 4.71% | 6.86% | |

**The model's premise is confirmed but its optimism is not.** Queue wait really is
serialisation: adding workers reduces it. But the reduction is 2.06x from four workers, not
the 4x a pure-serialisation model predicts, because per-item work doubled at the same time.
Four workers each running at half speed is twice the throughput, which is exactly what the
numbers say.

A local four-node cluster measured **4.01x** for the same change, with work duration rising
only 1.6 to 1.8x. At twelve nodes the contention is worse and eats half the benefit. Whatever
it is scales with worker count and with cluster size, and it has not been identified — the
cluster manager is still under 7% of a core, so it is not CPU.

This changes the relative value of the two candidate fixes. Threadiness is a constant factor
and that factor is now measured at about 2, not 4. Narrowing `ReconcileAll()` removes the
work rather than parallelising it, and the churn lane says 78% of reconciles during churn are
removable. The two compose, but the narrowing is now clearly the larger lever.

## Hypothesis 4 demotion: retracted

October demoted `FRRNodeState.status.runningConfig` size from Critical to Medium on a measured
9.7x compaction and 650x headroom. Those figures are superseded. **The October measurements
are not carried forward and nothing below depends on them**; the current reading of this
hypothesis rests only on the November runs, where every quoted snapshot passed the
[convergence test](#result-4-the-settle-heuristic-fails-intermittently-and-spread-proves-it).

| Shape | Config per node | Compaction | Headroom to 1.5 MB |
|---|---|---|---|
| 6 nodes, 20 RAs | 11,609 B / 11,512 B | 2.0x | 130x |
| 12 nodes, 20 RAs | 11,454 B | 2.1x | 131x |
| 12 nodes, 40 RAs | 20,587 B / 20,579 B | 2.3x | **73x** |

Two properties follow, and both are visible within this run set alone:

**Config size does not depend on node count.** Six nodes and twelve both give ~11.5 kB per node
at 20 RouteAdvertisements. Adding nodes adds objects but not per-node configuration, which is
consistent with each node carrying only its own view.

**It grows with network count, at roughly 454 B per network.** Fitting the two RA points,
11.5 kB at 20 and 20.58 kB at 40, gives a slope of 454 B and an intercept near 2.4 kB. The
1.5 MB etcd object limit therefore arrives at roughly **3,300 networks** — only 3.3x beyond
the 1000-CUDN target, and that is before EVPN, whose per-VRF stanzas do not share a neighbour
and so will not merge as well.

Compaction is **2.0 to 2.3x** and stable across all three shapes. **Hypothesis 4 returns to
High**: it is a genuine ceiling within sight of the target, not the distant one October
described.

## Next Activities

Two items from the previous revision are **done**: the settle heuristic now settles on node
agreement, and the threadiness A/B has run. What they produced reorders the rest.

**Find what contends under concurrency.** This is the new top item, because it bounds
everything else. Four workers doubled per-item work at twelve nodes and raised it only 1.6 to
1.8x at four, so the contention scales with both worker count and cluster size, and it halves
the benefit of the one tuning knob available. Cluster manager CPU peaks under 7% of a core, so
it is not compute. The candidates are apiserver-side contention, client-side rate limiting,
and a lock in the reconcile path that the race review did not reach. Registering client-go's
`rest_client_*` metrics would separate the first two in one run; the third needs the
call-graph audit below.

**Finish the race audit of the reconcile call graph.** The review done so far covered the
controller struct and the NAD annotation, and found one real lost-update race, now
[#7255](https://github.com/ovn-kubernetes/ovn-kubernetes/pull/7255). It did not cover
`generateFRRConfigurations`, `reconcileRouteAdvertisements`, `deleteRANetworks` or the
networkmanager calls they make. Finding a bug on the first look is a reason to keep looking,
and no threadiness default should move before this is complete.

**Narrow `ReconcileAll()`** ([Activity 4.1](05-roadmap.md#activity-41-narrow-reconcileall)).
Now clearly the larger lever rather than the follow-on. Threadiness is a constant factor and
that factor is measured at about 2, not the 4 a pure-serialisation model predicts. Narrowing
removes the work instead: the churn lane says 78% of reconciles during churn write nothing.
The distinction compounds, because amplification grows with the population — changing *k* of
*N* RouteAdvertisements costs O(k x N) reconciles, so the waste grows quadratically in the
quantity being scaled and no constant factor rescues it.

**Put a third point on the network axis.** The 3,300-network config ceiling is a line through
two points, 20 RAs and 40, extrapolated more than fortyfold. An 80-RA lane turns it into a
fitted slope and shows whether growth is linear or super-linear well before anything
approaches the limit.

**Add a 6-node churn lane.** The current churn lane confounds node count with churn, so the
amplification factor cannot be separated from the per-reconcile cost.

**Measure churn with overlapping selectors.** Every lane so far gives each RouteAdvertisements
its own network, which is the case where no two reconciles touch the same NAD. That is why the
lost-update race never fired in CI and why the threadiness A/B was safe to run before #7255.
The contended case is unmeasured, and with the fix in place it will retry rather than lose
updates, so retry cost under overlap is the thing to look at.

## Caveats

**The threadiness result is one run.** 2.06x at twelve nodes against 4.01x on a four-node
laptop cluster is a large enough gap to act on, but it rests on a single CI lane. The local
figure should be treated as superseded rather than as a second data point.

**Amplification has wide error bars**, 4.5x to 7x across three runs, because splitting the
creation phase from the churn phase depends on 30 s sampling. The waste share, 78 to 80%, is
the stable figure and does not share that weakness.

**The axes rest on two points each** — 6 and 12 nodes, 20 and 40 RouteAdvertisements. The 1.3%
fit across four lanes is striking, but it is a line through few points rather than a fitted
curve, and the extrapolations to 500 nodes and 3,300 networks inherit that.

**October figures are not comparable and are not used.** Per-node config on the identical
6-node 20-RA shape reads about five times larger than in October while the generated objects
are within 5% of each other. The cause has not been established and is not being pursued; the
October numbers are treated as belonging to a different system. Any trend spanning the two
dates would be unsound.

**Every lane uses disjoint network selectors**, the most favourable shape for concurrency.
Conclusions about threadiness do not transfer to deployments whose RouteAdvertisements
overlap.

**All of this is kind.** Twelve nodes sharing one kernel, one disk and one apiserver on a
32-core runner. The proportionality is worth extrapolating; the absolute latencies are not.
A local four-node cluster reproduced the model's *form* with constants 25% lower, which is
the shape of that limitation.
