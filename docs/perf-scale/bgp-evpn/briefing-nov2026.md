### Where each number comes from

Prometheus figures are indexed by kube-burner from the profile at
`contrib/perf/metrics-ovnk.yml` and land in the run artifact as
`<lane>-performance-test-data-<run-id>/perf/metrics/<metricName>.json`.

| Figure in this briefing | `metricName` | Query |
|---|---|---|
| Queue wait p99 | `ovnkubeWorkqueueQueueDuration99th` | `histogram_quantile(0.99, sum(rate(ovnkube_clustermanager_workqueue_queue_duration_seconds_bucket[2m])) by (name, le)) > 0` |
| Queue work p99 | `ovnkubeWorkqueueWorkDuration99th` | same, on `..._work_duration_seconds_bucket` |
| Reconcile count | `raReconcileCount` | `sum(ovnkube_clustermanager_route_advertisements_reconcile_duration_seconds_count) by (result)` |
| Reconcile p99 | `raReconcileDuration99th` | `histogram_quantile(0.99, sum(ovnkube_clustermanager_route_advertisements_reconcile_duration_seconds_bucket) by (result, le)) > 0` |
| create / unchanged writes | `raFRRConfigurationProcessed` | `sum(ovnkube_clustermanager_route_advertisements_frr_configuration_processed_total) by (op)` |
| OVN DB size, txn rate, txn p99 | `ovnDBSizeBytes`, `libovsdbTxnRate`, `libovsdbTxnDuration99th` | see the profile |

Queue figures are filtered to the single series
`name="clustermanager routeadvertisements controller"`.

Quantities Prometheus cannot hold — generated-object counts and bytes, `FRRNodeState` sizes,
session states, the peer's view — come from the `beforeCleanup` hook
`contrib/perf/collect-bgp-state.sh`, which writes `bgp-state-<lane>.json` into the same
artifact. CPU and memory come from `performance_report.md`, generated by
`contrib/perf/generate_perf_report.py` from cAdvisor.

## Executive Summary

The scale ladder ran twice: four lanes, each adjacent pair isolating one variable. The second
run widened a histogram that the first run had pinned, and that unlocked the result.

**Queue wait is exactly proportional to the generated object count.** Three lanes fit
`wait p99 = 0.1355 s x (nodes x RAs)` to within 0.5%, and work duration fits
`0.1698 s x nodes` to within 0.1%. Both axes of the ladder are now a single equation.

**Hypothesis 1 is confirmed and reproduced.** 80% of all RouteAdvertisements reconciles write
nothing, identically in both runs, and every wasted reconcile writes exactly one object per
node.

**Two measurements still cannot be trusted, and a cheap discriminator now proves which.**
Per-node config spread separates converged snapshots (0.1 to 0.5%) from mid-convergence ones
(14 to 31%) with nothing in between.

## Measurement Setup

| Lane | Nodes | RAs | Generated objects | Isolates |
|---|---|---|---|---|
| `bgp-ra-density` | 6 | 20 | 120 | baseline |
| `bgp-ra-density-wide` | 12 | 20 | 240 | node count, vs density |
| `bgp-ra-density-deep` | 12 | 40 | 480 | RA count, vs wide |
| `bgp-ra-churn` | 12 | 40 | 480 | churn, vs deep |

Node count is `num-workers` plus `KIND_NUM_INFRA` of 2 plus the control plane. The fan-out
identity `RAs x nodes` held exactly in all four lanes of both runs, and every
RouteAdvertisements reached `Accepted` every time, including after five churn cycles with no
leaked or missing generated objects.

**Query coverage is complete**: 26 of 27 queries returned data in every lane. The exception,
`ovnNorthdTxnTryAgainRate`, is genuinely zero — northd had no transaction retries.

## Result 1: widening the buckets, and why the result is trustworthy

`ExponentialBuckets(.001, 2, 16)` reaches 32.768 s. Run 42220334668 pinned both 40-RA lanes
there. Run 42229126637 used 20 buckets, reaching 524.288 s.

| Lane | Run 1, 16 buckets | Run 2, 20 buckets | |
|---|---|---|---|
| density | 16.302 s | **16.269 s** | unchanged — control |
| density-wide | 32.178 s | **32.440 s** | unchanged — control |
| density-deep | 32.768 s *(pinned)* | **65.208 s** | was hiding a factor of 2 |
| churn | 32.768 s *(pinned)* | **61.669 s** | was hiding a factor of 1.9 |

The two lanes that were never saturated did not move. That is what makes the other two
believable: the rebucketing moved the ceiling, not the measurement. No sample sits on a
boundary in run 2.

Only this family needed it. `route_advertisements_reconcile_duration_seconds` uses a `.005`
base and reaches 40.96 s; its highest reading is 2.163 s. Queue wait is the term that outgrows
the rest because it accumulates over the whole queue while work duration stays per item.

## Result 2: both axes collapse into one equation

| Lane | Nodes | RAs | Objects | Wait p99 | **Wait / object** | Work p99 | **Work / node** |
|---|---|---|---|---|---|---|---|
| density | 6 | 20 | 120 | 16.269 s | 0.1356 | 1.018 s | 0.1697 |
| density-wide | 12 | 20 | 240 | 32.440 s | 0.1352 | 2.038 s | 0.1698 |
| density-deep | 12 | 40 | 480 | 65.208 s | 0.1359 | 2.038 s | 0.1698 |

```
queue wait p99 = 0.1355 s x (nodes x RAs)    three points, 0.5% spread
work duration  = 0.1698 s x nodes            independent of RA count, 0.1% spread
```

Work depends only on node count, because a reconcile is one apiserver write per node. Wait
depends on the **product**, because every generated object queues behind every other through a
single worker. The wait-to-work ratio is therefore just the RA count: 16.0x at 20 RAs, 32.0x
at 40.

This supersedes the October model, which had only the node axis. The RA axis was unmeasurable
until the buckets were widened.

**Extrapolation**, at 0.1355 s per object with `Threadiness: 1`:

| Shape | Objects | Predicted queue wait |
|---|---|---|
| 24 nodes x 40 RAs | 960 | 2.2 min |
| 120 nodes x 50 RAs | 6,000 | 13.6 min |
| 500 nodes x 50 RAs | 25,000 | 56.5 min |
| 500 nodes x 1000 RAs | 500,000 | **18.8 h** |

## Result 3: hypothesis 1 confirmed, and reproduced

The churn lane holds 40 RouteAdvertisements steady and deletes and recreates 4 of them, five
times. Run 2:

| | At creation complete | At run end | Churn-attributable |
|---|---|---|---|
| Reconciles | 107 | 196 | **+89** |
| `unchanged` writes | 804 | 1,872 | **+1,068** |
| `create` writes | 480 | 480 | **0** |

**Every churn reconcile was pure waste.** 1,068 / 89 = **12.0 writes per reconcile**, exactly
the node count, and not one of them a create. Each regenerated the full configuration for its
RouteAdvertisements, compared it, found it identical, and wrote nothing.

Across the whole run, **156 of 196 reconciles (80%) produced no configuration change**.

### What reproduces and what does not

| Quantity | Run 1 | Run 2 | |
|---|---|---|---|
| Writes per wasted reconcile | 12.0 | 12.0 | exact |
| Share of reconciles writing nothing | 80% | 80% | exact |
| Churn-attributable reconciles | +127 | +89 | **varies** |
| Amplification per RA changed | 6.35x | 4.45x | **varies** |

The invariants are exact; the amplification factor is not. That is an artifact of the analysis
rather than the system: splitting creation from churn depends on which 30 s sample first shows
`create` reaching 480, and the two runs crossed that threshold at different points. Read the
amplification as **4.5x to 6.4x** and the 80% waste as the solid figure.

!!! note "Why the density lanes cannot show this"

    They create each RouteAdvertisements once and nothing else changes, so there is no
    amplification to observe: all three report exactly one reconcile per RA and zero
    `unchanged` writes. The October briefing marked hypothesis 1 confirmed on indirect
    evidence and then [withdrew it](08-first-ci-results.md#corrections). The churn lane was
    built to settle it, and has now done so twice.

**This likely understates the problem.** kube-burner recreates a deleted object about a second
after deleting it, and `create` never increased during churn, so the controller never observed
the gap and coalesced each pair into one event. Real churn, seconds or minutes apart, would
produce two fan-out events rather than one.

## Result 4: the settle heuristic fails intermittently, and spread proves it

`wait_for_settle()` in the hook polls every 5 s and declares convergence when the generated
count and total `runningConfig` bytes match the previous poll. frr-k8s reloads nodes in waves
and the total plateaus between them, so two matching polls do not mean converged.

Adding per-node spread to the comparison makes it unambiguous:

| Lane | Run 1 spread | Run 2 spread | |
|---|---|---|---|
| density | 6 B (0.1%) | 9 B (0.1%) | converged |
| density-wide | 8 B (0.1%) | **3,385 B (31.1%)** | run 2 mid-convergence |
| density-deep | **3,928 B (23.2%)** | **2,616 B (13.8%)** | both mid-convergence |
| churn | 103 B (0.5%) | 99 B (0.5%) | converged |

The distribution is bimodal — 0.1 to 0.5% against 14 to 31%, nothing between — and **wide
flipped between runs on an identical shape**, so this is a race rather than a property of the
larger lanes. Every node carries all 40 networks, so at convergence they must agree; a spread
of a quarter of the value is reload waves in flight.

Taking only the trustworthy snapshots:

| Shape | Config per node | Reproducibility |
|---|---|---|
| 6 nodes, 20 RAs | 11,609 B / 11,512 B | 0.8% |
| 12 nodes, 20 RAs | 11,454 B (run 1 only) | — |
| 12 nodes, 40 RAs | 20,587 B / 20,579 B | 0.04% |

**Config size is independent of node count** — 6 and 12 nodes both give ~11.5 kB at 20 RAs —
and grows with network count at roughly **454 B per RA**. Linear extrapolation puts the 1.5 MB
etcd object limit near **3,300 networks**.

## Hypothesis 4 demotion: retracted

October demoted `FRRNodeState.status.runningConfig` size from Critical to Medium on a measured
9.7x compaction and 650x headroom. Neither figure survives.

| Shape | Config per node | Compaction | Headroom to 1.5 MB |
|---|---|---|---|
| 6 nodes, 20 RAs (October) | 2,306 B | 9.7x | 650x |
| 6 nodes, 20 RAs (November) | 11,512 B | 2.0x | 130x |
| 12 nodes, 40 RAs (November) | 20,579 B | 2.3x | **73x** |

Compaction is **2.0 to 2.3x, not 9.7x**, and the axis is network count rather than node count.
**Hypothesis 4 should return to High.**

**One unexplained change blocks acting on this.** The 6-node 20-RA shape is identical between
October and November, yet per-node config grew roughly **5x** while the generated objects grew
only 4.7% (133,728 B to 139,968 B). The inputs barely moved and the merged output quintupled.
That needs bisecting before the numbers above are relied on in either direction.

## Next Activities

**Switch the settle heuristic to per-node uniformity.** Spread separates the two populations
cleanly, so settle when `max - min` falls below a small fraction of the value, keeping a
stability check as the fallback for workloads where nodes legitimately differ. Without it,
roughly half the `FRRNodeState` readings are unusable and which half is a coin toss.

**Bisect the 5x config growth** between October and November on the unchanged 6-node 20-RA
shape. Cheaper things to try first: diff a rendered `runningConfig` against the October base,
read the log over `routeadvertisements/controller.go` and `rawconfig.go` for that window, and
check whether the frr-k8s pin moved. Full bisect only if those come up empty.

**Run the threadiness A/B** ([P2b](05-roadmap.md#phase-p2b-threadiness-ab)). It remains cheap
and it falsifies the model: if four workers do not move wait p99, the limit is not
serialisation and the equation above needs rethinking.

**Then narrow `ReconcileAll()`** ([Activity 4.1](05-roadmap.md#activity-41-narrow-reconcileall)).
Threadiness is a constant factor — four workers, four times the throughput, and the same wasted
writes performed concurrently. Narrowing removes the work. The distinction matters because
amplification grows with the population: changing *k* RAs out of *N* costs O(k x N) reconciles,
so the waste grows quadratically in the quantity being scaled, and no constant factor rescues
that. Threadiness lands sooner; narrowing changes the complexity class, and the churn lane has
given it a measured 80% target.

**Add a 6-node churn lane.** The current one confounds node count with churn, so the
amplification factor cannot be separated from the per-reconcile cost.

---

## Caveats

**Amplification has wide error bars**, 4.5x to 6.4x, because the creation/churn phase split
depends on 30 s sampling. The 80% waste figure does not share that weakness.

**Half the `FRRNodeState` readings are mid-convergence**, and the briefing uses only the
snapshots whose spread says they converged.

**The RA axis rests on two points** — 20 and 40 — and the node axis on two, 6 and 12. The 0.5%
fit across three lanes is striking, but it is a line through few points, not a fitted curve.

**All of this is kind.** Twelve nodes sharing one kernel, one disk and one apiserver on a
32-core runner. The proportionality is worth extrapolating; the absolute latencies are not.
