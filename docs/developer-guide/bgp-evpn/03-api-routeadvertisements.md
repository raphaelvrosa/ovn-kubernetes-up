# 03 — API: RouteAdvertisements

The `RouteAdvertisements` custom resource is the only user intent object of the
BGP route export feature. Everything the cluster manager generates, everything
the zone controllers program in OVN and everything the node programs in the
host stack is derived from it, from the `FRRConfiguration` objects it selects
and from the networks it selects.

## Field reference

### `spec.targetVRF` (optional, string)

Which VRF the selected networks' prefixes are advertised **in**. Three
semantic values exist, and the controller treats them differently in
`generateFRRConfiguration` (`controller.go:1286-1325`):

| Value | Meaning | Router matched in the source `FRRConfiguration` | Prefixes placed in the router |
|---|---|---|---|
| unset (`""`) | Advertise in the default VRF | The router whose `vrf` is empty | All selected networks' per-node prefixes (`selectedNetworks.hostSubnets`) |
| `auto` | Advertise each network in **its own** VRF | For each router, the router whose `vrf` equals a selected network's VRF name; a router with empty `vrf` matches the default network only if it is selected | That one network's per-node prefixes |
| any other name | Advertise in that specific VRF | The router whose `vrf` equals the value | All selected networks' per-node prefixes |

Only `auto` and the empty string have special meaning. A literal VRF name is
accepted only if it is a valid Linux interface name (`controller.go:572-576`,
`validation.go:154`), because it is written verbatim into FRR configuration.

Two rules follow from the value:

- `EgressIP` advertisement is rejected with `auto` (`controller.go:569-571`).
- An EVPN network requires `auto` or exactly its own VRF name
  (`controller.go:665-668`).

### `spec.networkSelectors` (required)

Uses the shared `types.NetworkSelectors` type from
`go-controller/pkg/crd/types`. Only two selection types are allowed by the CEL
rule on the spec (`types.go:32`): `DefaultNetwork` and
`ClusterUserDefinedNetworks`. Namespaced `UserDefinedNetwork`s and secondary
networks cannot be advertised.

- `DefaultNetwork` selects the cluster default network. The controller ensures
  the internal default-network `NetworkAttachmentDefinition` exists when it
  resolves this selector (`controller.go:2171-2177`, `util.EnsureDefaultNetworkNAD`).
- `ClusterUserDefinedNetworks.networkSelector` is a label selector evaluated
  against **NetworkAttachmentDefinition labels**, filtered to NADs whose
  controller owner reference is a `ClusterUserDefinedNetwork`
  (`controller.go:2178-2193`). The CUDN controller copies CUDN labels to the
  NADs it renders, which is why selecting by CUDN label works.

### `spec.nodeSelector` (required)

Standard label selector over `Node` objects. The CEL rule on the spec
(`types.go:31`) forbids a non-empty selector when `PodNetwork` is advertised:
pod subnets must be announced from every node or traffic breaks. The controller
re-checks the same condition at reconcile time (`controller.go:704-706`).

An empty selector is **required**, not merely allowed, for `PodNetwork`. A
non-empty selector is only legal for an RA that advertises `EgressIP` alone.

### `spec.frrConfigurationSelector` (required)

Label selector over `FRRConfiguration` objects in any namespace. The selected
objects are **templates**: the controller copies each one, keeps only the
routers that match the target VRF rules above and rewrites their prefixes and
neighbor filters. Objects whose name starts with `ovnk-generated-` are ignored
even if the selector matches them (`controller.go:737-741`), so an RA can never
feed on its own output.

### `spec.advertisements` (required, 1 or 2 unique entries)

| Value | Effect |
|---|---|
| `PodNetwork` | Advertise the pod subnets of the selected networks. Per-node host subnets for Layer3 and the default network, the whole network subnet for Layer2 (`controller.go:899-915`). |
| `EgressIP` | Advertise, from each selected node, the egress IPs assigned to that node whose `EgressIP` namespace selector matches a namespace served by a selected network (`controller.go:2207-2269`). Requires the EgressIP feature to be enabled. Not supported for Layer2 networks nor with `targetVRF: auto`. |

## Admission-time validation (CEL)

Rules are declared as kubebuilder markers in `types.go` and rendered into the CRD.

| Location | Rule | Message |
|---|---|---|
| `types.go:31` | `(!has(self.nodeSelector.matchLabels) && !has(self.nodeSelector.matchExpressions)) \|\| !('PodNetwork' in self.advertisements)` | If 'PodNetwork' is selected for advertisement, a 'nodeSelector' can't be specified as it needs to be advertised on all nodes |
| `types.go:32` | `!self.networkSelectors.exists(i, i.networkSelectionType != 'DefaultNetwork' && i.networkSelectionType != 'ClusterUserDefinedNetworks')` | Only DefaultNetwork or ClusterUserDefinedNetworks can be selected |
| `types.go:56-58` | `MinItems=1`, `MaxItems=2`, `self.all(x, self.exists_one(y, x == y))` | Entries must be unique |
| `types.go:64` | `Enum=PodNetwork;EgressIP` | |

CRD admission tests for these rules belong in `test/crd-integration/`, not in
e2e (see [19 — Testing and CI](19-testing-and-ci.md)).

## Controller-time validation

Everything not expressible in CEL is checked by the cluster manager in
`generateFRRConfigurations` and surfaced in `status`. The full list, with the
error class each one maps to, is in
[07 — RouteAdvertisements controller, section "Validation and error classes"](07-cm-routeadvertisements-controller.md#validation-and-error-classes).
The classes are:

| Class | Sentinel | Status reason | Retried by the workqueue? |
|---|---|---|---|
| Configuration error | `errConfig` (`controller.go:71`) | `ConfigurationError` | No, waits for a new event |
| Pending input | `errPending` (`controller.go:72`) | `ConfigurationPending` | No, waits for a new event |
| Unsafe FRR input | `errUnsafeFRRInput` (`validation.go:21`, wraps `errConfig`) | `ConfigurationError` | No, and existing unvalidated `FRRConfiguration`s are deleted |
| Invalid VTEP annotation | `errInvalidVTEP` (`controller.go:73`, wraps `errConfig`) | `ConfigurationError` | No, but the sanitized desired state is still applied |
| Anything else | | `InternalError` | Yes, with rate limiting, until `MaxAttempts` |

## Status contract

```go
// go-controller/pkg/crd/routeadvertisements/v1/types.go:83-97
type RouteAdvertisementsStatus struct {
	Status string `json:"status,omitempty"`
	Conditions []metav1.Condition `json:"conditions,omitempty" patchStrategy:"merge" patchMergeKey:"type"`
}
```

- `status.status` is a free-form string shown by `kubectl get ra`. It is
  either `Accepted` or `Not Accepted: <error>` (`controller.go:2100-2105`).
- `status.conditions` holds exactly one condition type, `Accepted`
  (`types.go:77`, `RouteAdvertisementsAccepted`). It is written with
  server-side apply under the field manager
  `clustermanager-routeadvertisements-controller` (`controller.go:63`,
  `controller.go:2139-2153`).
- `observedGeneration` is set to `metadata.generation`
  (`controller.go:2121`). Consumers that must know the RA was accepted **for
  the spec they can see** compare the two; the network manager does exactly
  that (`networkmanager/network_controller.go:614`).

| Condition `Accepted` | reason | When |
|---|---|---|
| `True` | `Accepted` | Generation succeeded, FRRConfigurations and NAD annotations were applied. |
| `False` | `ConfigurationPending` | A required input is not there yet, for example no node has the subnet annotation, no FRRConfiguration matches, no network matches. |
| `False` | `ConfigurationError` | The spec, the selected networks, the selected FRRConfigurations or a node VTEP annotation are inconsistent. |
| `False` | `InternalError` | An API call or lister failed repeatedly; the key was dropped from the queue after `MaxAttempts` and `HandleError` wrote the status (`controller.go:181-194`). |

The message is trimmed to the maximum condition length by
`util.MergeStatusCondition`, and the last transition time is preserved when the
status value does not change (`controller.go:2113-2122`).

A metric mirrors the condition:
`ovnkube_clustermanager_route_advertisement_condition{name,condition,status}`
(`go-controller/pkg/metrics/cluster_manager.go:136-143`), recorded on every
reconcile including no-op ones so it survives controller restarts
(`controller.go:2124-2129`), and deleted when the RA is deleted
(`controller.go:404`).

## Annotations and labels written because of a RouteAdvertisements

| Object | Key | Value | Writer | Reader |
|---|---|---|---|---|
| Generated `FRRConfiguration` | label `k8s.ovn.org/route-advertisements` | RA name | RA controller (`controller.go:1722-1726`) | RA controller to list its own output; `conflictingVTEPNodes` |
| Generated `FRRConfiguration` | annotation `k8s.ovn.org/route-advertisements` | `<ra>/<sourceFRRConfiguration>/<node>` | RA controller (`controller.go:1727-1735`) | RA controller to diff desired vs existing |
| Generated `FRRConfiguration` | annotation `k8s.ovn.org/route-advertisements-validated` | `"true"` | RA controller | RA controller to purge objects created before input validation existed |
| `NetworkAttachmentDefinition` of every selected network | annotation `k8s.ovn.org/route-advertisements` | JSON array of RA names, for example `["default","blue"]` | RA controller (`controller.go:2021-2089`) | Network manager on ovnkube-controller and ovnkube-node (`network_controller.go:579-583`) |

The constants are `types.OvnRouteAdvertisementsKey` and
`types.OvnRouteAdvertisementsValidatedKey` (`go-controller/pkg/types/const.go:236-239`).

The NAD annotation is the **only** channel through which the zone and node
controllers learn that a network is advertised. They never watch
`FRRConfiguration`s. See [11 — Network manager propagation](11-network-manager-propagation.md).

## Relationships with other objects

```mermaid
flowchart LR
    RA[RouteAdvertisements]
    FRRsrc[FRRConfiguration<br/>user authored]
    FRRgen[FRRConfiguration<br/>ovnk-generated-*]
    NAD[NetworkAttachmentDefinition]
    CUDN[ClusterUserDefinedNetwork]
    Node[Node]
    EIP[EgressIP]
    VTEP[VTEP]

    RA -- frrConfigurationSelector --> FRRsrc
    RA -- networkSelectors --> NAD
    CUDN -- owns --> NAD
    RA -- nodeSelector --> Node
    RA -- advertisements: EgressIP --> EIP
    RA == generates ==> FRRgen
    RA == annotates ==> NAD
    CUDN -. evpn.vtep .-> VTEP
    Node -. k8s.ovn.org/vteps .-> RA
    Node -. k8s.ovn.org/node-subnets .-> RA
```

- A CUDN with `transport: EVPN` or `transport: NoOverlay` is **not accepted**
  (`TransportAccepted=False`) until an RA that selects it, advertises
  `PodNetwork` and is itself `Accepted=True` exists. See
  [10 — CUDN transport validation](10-cm-cudn-transport-and-no-overlay.md).
- In managed no-overlay mode the RA itself is created by the managed BGP
  controller and named `ovnk-managed-bgp-default` or `ovnk-managed-bgp-cudn`.
  See [08 — Managed BGP controller](08-cm-managed-bgp-controller.md).
- Several RAs may select the same network. The network manager unions the VRFs
  they advertise into per node (`network_controller.go:636-649`).
- Several RAs may advertise EVPN networks that share the default-VRF underlay.
  The VTEP host route each node advertises is compared across RAs
  (`controller.go:1030-1205`).

## Worked examples

### Advertise a CUDN over the default VRF and import default-VRF routes into it

```yaml
apiVersion: k8s.ovn.org/v1
kind: RouteAdvertisements
metadata:
  name: default-cudn
spec:
  targetVRF: default         # same as leaving it unset
  advertisements: [PodNetwork]
  nodeSelector: {}
  frrConfigurationSelector:
    matchLabels:
      use-for-advertisements: default
  networkSelectors:
  - networkSelectionType: ClusterUserDefinedNetworks
    clusterUserDefinedNetworkSelector:
      networkSelector:
        matchLabels:
          advertise: "true"
```

With `targetVRF` not `auto`, the generated router carries reciprocal imports:
the matched default-VRF router gets `imports: [{vrf: <network vrf>}]` and an
extra router `vrf: <network vrf>, imports: [{vrf: default}]` is appended
(`controller.go:1494-1531`). The feature doc shows the resulting object in
[route-advertisements.md](../../features/bgp-integration/route-advertisements.md#frrconfiguration-instances-generated-by-ovn-kubernetes).

### VRF-Lite

```yaml
spec:
  targetVRF: auto
  advertisements: [PodNetwork]
  nodeSelector: {}
  frrConfigurationSelector:
    matchLabels:
      use-for-advertisements: extranet   # the source must have a router with vrf: extranet
  networkSelectors:
  - networkSelectionType: ClusterUserDefinedNetworks
    clusterUserDefinedNetworkSelector:
      networkSelector:
        matchLabels:
          advertise: "true"
```

If the source has no router for a selected network's VRF, the RA is
`Not Accepted` with
`FRRConfiguration "<name>" selected for node "<node>" has no VRF matching the RouteAdvertisements target VRF or any selected network`
(`controller.go:1012-1013`), unless the network is simply inactive on that
node under dynamic UDN allocation (`frrConfigOnlyMatchesInactiveNetworks`,
`controller.go:1247`).

### EVPN

```yaml
spec:
  targetVRF: auto
  advertisements: [PodNetwork]
  nodeSelector: {}
  frrConfigurationSelector:
    matchLabels:
      use-for-advertisements: evpn       # the source must have a default-VRF router with neighbors
  networkSelectors:
  - networkSelectionType: ClusterUserDefinedNetworks
    clusterUserDefinedNetworkSelector:
      networkSelector:
        matchLabels:
          evpn: enabled
```

The default-VRF router in the source is the EVPN underlay session; its
neighbors are activated in `address-family l2vpn evpn` through raw FRR config
(`rawconfig.go:219-258`). See [06 — FRRConfiguration contract](06-frrconfiguration-contract.md).

## Review notes

When reviewing a change that touches this API:

- Any new spec field must be reflected in `raNeedsUpdate`
  (`controller.go:2292`), which only looks at `metadata.generation`; a new
  field that does not bump generation (status, annotations) will not trigger a
  reconcile.
- The notifier used by the CUDN controller filters RA updates to selector,
  advertisements, `targetVRF` and the `Accepted` condition
  (`clustermanager/userdefinednetwork/notifier/routeadvertisements.go:309-337`).
  Add the field there if CUDN transport acceptance depends on it.
- The network manager's `raNeedsUpdate` (`network_controller.go:684`) ignores
  RA add and delete events on purpose and relies on the NAD annotation; a
  change in how the controller annotates NADs changes what every node sees.
- `kubectl explain` text comes from the Go doc comments; keep them in sync
  with the CEL messages.
